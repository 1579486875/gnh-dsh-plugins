# dsh-self-heal（失控自愈）

> 原名 `dsh-loop-guard`。既然它已经不只是「拦住」，而是「救回来」，就换个名
> 字 —— 中文可以叫它**失控自愈**。

给 DSH 加一层自愈能力。它不只是把跑飞的请求掐掉，而是**把对话救回来**：

| 出什么事 | 它怎么办 |
|---|---|
| 模型陷入复读、原地打转 | 熔断 → 压缩历史 → 用压缩后的历史重新发一次请求，接着干 |
| 一次调用迟迟不结束（还在吐字，所以空闲超时永远不触发） | 熔断 → 压缩历史 → 重发一次，接着干 |
| 模型**光想不说**：思考写了一大堆，正文一个字没输出 | 一轮结束前先压缩上下文腾地方，再补一句提醒，让这一轮**再跑一步**，把正文真正写出来 |
| 模型**说了一半就停**：话说到一半、也没去调工具（实测原话：写完「先确认 README 第二节的真实设置项，避免我写的新表与它不符。」就没了下文） | 同样先压缩、再提醒它接着写完 |
| 模型**短句打转**：思考流里连着几百行「好。／行动。／（调用。）／NOW.」，措辞每次略变，但翻来覆去就是那几句，始终不真的去调工具 | 熔断 → 压缩历史 → 把失败原因告诉模型 → 重发 |
| 模型**动作打转**：同一套工具调用（参数也几乎一样）走了好几遍，问题却一直没解决 | 往下一步的上下文里塞一句提醒，让它换办法 |

## 一、它解决什么问题

翻车现场长这样：接一个第三方中转模型进 DSH，让它统计个数据，结果模型陷进
推理循环，单次请求吐出几千万 token，账号直接被刷到欠费。

DSH 原本已经有几道保护，但它们各自有明确的作用域：

| 层 | 机制 | 怎么被绕过去 |
|---|---|---|
| 单次请求输出 | `llm-deepseek.maxTokens`（默认 256000） | 第三方网关**直接忽略**请求里的上限字段 |
| 流空闲 | `streamIdleTimeoutMs`（默认 5 分钟） | 只判「不吐字」；持续吐字时永不触发 |
| 工具重复 | `dsh-repeat-tool-reminder`（3/5/8 次） | 只发**提醒**，模型不理它就继续转 |
| 上下文溢出 | `dsh-compaction-basic`（`CONTEXT_WINDOW_EXCEEDED`） | 只在**提供方明确报溢出**时才动手；复读和超时它不管 |

于是剩下两件事没人管 —— 而本插件管这两件事，并且**管到底**：

1. **复读熔断** —— 正面对付「思考打转」，这是事故的正主；
2. **墙钟总时长超时** —— 兜底「一直吐字、永不空闲」这类卡死。

⚠️ **注意：本插件不再有「单次输出上限」。** 旧版（`dsh-loop-guard`）有一道
「单次请求超过 N token 就掐断」的硬闸门，它的问题是一刀切 —— 合法的超长输出
（批量生成、大段代码、长表格）也会被杀掉。现在只在**识别出失控特征**时才介入，
正常的长输出不再受任何总量限制。

## 二、三道机制，分别在哪儿动手

插件挂在 host 组合上，监听三个官方扩展点，一件事一个：

```
   模型开始输出
        │
        ▼
 ① llm/stream  ── 边看边判断「是不是跑飞了」（复读 / 墙钟超时）
        │
        │  判定失控 → 关掉上游、补一个终止 finish
        ▼
 ② agent/request-error ── 把对话救回来
        压缩历史 → 返回 {kind:'retry'}
        → agent 循环用压缩后的历史重新发请求

   一轮即将结束（模型不再欠工具调用）
        │
        ▼
 ③ agent/turn-stopping ── 治「没说完就停」
        这一轮没有正文？或者正文说了半截？
        → 先压缩上下文腾地方（压不动也照样往下走）
        → 再注一条提醒，让本轮再跑一步接着写完
```

### ① 发现失控：`llm/stream`

这是模型输出的必经之路，所以能实时看到每一个分片。

- **复读检测**：两条线并行，任一命中即熔断。
  - **字符级**：在尾部窗口里从短到长枚举候选周期，只要连续 `minRepeats`
    段完全一致就判命中 —— 抓「同一句话反复念」。
  - **行级**：把尾部切成有效行，寻找最小的「行块周期」—— 抓循环体很长、
    字符窗口装不下的多行循环（事故里那种 15~18 行的英文推理反复念）。
- **短句打转检测**：抓另一种失控 —— 措辞每次都在微调，但翻来覆去就是那几句
  **超短句**，下面这种（思考流里的真实截图，连着几百行）：

  ```
  好。 ／ 行动。 ／ 执行。 ／ 好。 ／ 我调用工具。 ／ 好。 ／ Go.
  （真的调用了。）好。 ／ NOW. ／（调用。）／ 我调用 write 工具。 ／ ……
  ```

  严格周期在这里根本不存在（所以前两条线抓不到它），能认的只有**统计特征**：
  平均行长极短 + 短句密度高 + 短句重复率高，**三条同时成立**才动手。
  详细闸门见第七节与第八节。
- **时长检测**：从这次调用开始到现在的真实时间（墙钟）超过上限就熔断 ——
  它是「流空闲超时」的兜底。

两条线都**不要求周期在末尾对齐**。这一点是必须的：流式输出常常停在半行或
半句话上，末尾也可能挂着一句收尾语（实测中子代理就诚实地在复读末尾加了一个
`VERIFY-OK` 标记）。只认「末尾对齐」会让这类循环整个漏掉，所以判定会从末尾
往回尝试若干偏移。

> 这个对齐问题正是**端到端验证**抓出来的：单元测试当时的样本末尾恰好对齐，
> 27 个用例全绿；真实子代理的输出末尾多了一句收尾语，检测器就完全失灵。
> 现在有 4 个专门的回归用例钉住它。

### ② 救回来：`agent/request-error`

熔断之后，插件**不抛异常**，而是补一个带自定义 failure code 的终止 `finish`
分片。agent 循环看到请求失败，就会调用 `agent/request-error` 这个「恢复点」，
插件在那里接手：

```
识别熔断 → 查本轮恢复次数（有上限，绝不无限重试）
        → 让压缩服务强制做一次有用的缩减（ctx.compaction.compactIfNeeded）
        → 历史确实变短了？  是 → 返回 {kind:'retry'}
                            否 → 默认也给一次重试机会（可配置关掉）
```

返回 `{kind:'retry'}` 之后，agent 循环会**重新构建请求** —— 而请求是从「当前
历史」重新拼出来的，所以压缩出来的摘要会真的生效，这一次就有希望正常收尾。

两个刻意的选择：

- `reason.kind` 用 `'error'`，因此 `dsh-llm` 自己的流协议不变式照常通过
  （它允许 error / aborted 在内容块还没闭合时终止）；
- `failure.code` 用 `SELF_HEAL_*` 前缀，**刻意避开** `dsh-llm-retry` 的默认
  可重试白名单（`EMPTY_RESPONSE / RATE_LIMIT / SERVER / TIMEOUT / TRANSPORT`），
  所以官方重试不会把一次熔断再放大成五倍账单；重试与否由本插件自己决定。

### ③ 治好「没说完就停」：`agent/turn-stopping`

这个事件在「一轮即将结束、且模型已经不欠任何工具调用」的那一刻触发，正好是
判断「它到底有没有把话说完」的最佳时机。它管两种情况：

**情况一：光想不说。** 有些模型（推理型尤其常见）会把整个回合都花在思考上，
正文一个字不写；由于思考内容也算「有内容块」，官方的空响应重试
（`EMPTY_RESPONSE`）抓不到它 —— 用户看到的是一条「什么都没有」的回复。

**情况二：说了一半就停。** 正文写出来了，但明显没写完，而且也没有接着去调
工具。四条判据，按可靠性从高到低：

| 判据 | 例子 | 可靠性 |
|---|---|---|
| 提供方报告被长度上限截断（`max-tokens`） | — | 铁证 |
| 代码块没闭合（尾部 ``` 是奇数个） | 写了个 ` ```js ` 就没了 | 高 |
| 停在悬空标点上 | 以「，」「：」「；」结尾 | 高 |
| 最后一句是「我接下来要去做某事」 | 「先确认 README 第二节的真实设置项…」 | 中（可关） |

命中之后**先压缩、再提醒**，顺序是刻意的：

```
命中 → 让压缩服务压缩一次历史（腾出上下文空间）
     → 往会话里投一条提醒（steering），让这一轮再跑一步
```

为什么先压缩：说一半就停，多半是上下文已经太满、模型没地方把话写完了；不腾
地方就催它继续，它往往再停一次。**但压缩只是腾地方的手段，不是继续输出的
前提** —— 压缩服务不在、压缩报错、压缩没找到可压的区间，这三种情况都照常提醒
并继续（日志里会写明是哪一种）。

提醒次数有上限（默认同一轮 2 次），也有时效限制（默认 5 分钟），所以不会把
对话拖进新的死循环。同一轮里只有**第一次**命中才压缩 —— 反复压会把上下文越压
越薄。

> **为什么不判「结尾没有句号」**：正常回复以代码块、表格、列表项结尾太常见了，
> 它们本来就不带句号。按那条规则判，会把大量正常回答误判成「没说完」，然后追着
> 模型让它继续 —— 比原来的毛病还烦人。**宁可漏判，也不误报**，这是本项目对所有
> 启发式判据的统一取向。

## 三、安装位置与挂载层

- 插件源码：`%USERPROFILE%\.dsh\external\dsh-self-heal`
- 用 junction 挂进 `profiles\<名字>\node_modules\dsh-self-heal`
- 登记为 profile 的 bundle（`profiles\<名字>\package.json` 的
  `dependencies` + `dsh.profile.bundles`）

**挂在 host 平面是有意为之**：自愈要覆盖「所有会话 × 所有子代理 × 所有辅助
模型调用」的每一次模型请求。

> 一个实现细节值得一提：压缩服务 `ctx.compaction` 被官方 `isolate` 在**每个
> 会话各自的预设**里，host 平面直接 `ctx.get('compaction')` 往往拿不到。插件
> 因此按三条路依次尝试：官方的 `agentPresets.serviceFor(agent, 'compaction')`
> → `agent.ctx.get('compaction')` → `ctx.get('compaction')`；三条都拿不到就
> 优雅降级成「不压缩，直接重试一次」。

## 四、配置

默认走插件自带值，不用配。要调就在 `profiles\<名字>\cordis.patch.yml` 里按
id 覆盖：

```yaml
- id: self-heal
  config:
    enabled: true
    maxDurationMs: 1800000      # 单次调用的墙钟上限（毫秒）；0 = 关闭这项
    logTrips: true              # 每次介入都往日志写一行诊断
    recover:                    # 熔断之后怎么救
      enabled: true
      maxAttempts: 3            # 同一轮最多救几次
      retryWithoutCompaction: true   # 压缩没压动时，还给不给一次重试机会
      explainFailure: true      # 重发前把「刚才为什么失败」告诉模型（别盲目重发）
    unfinished:                 # 「没说完就停」怎么治（光想不说 + 说了一半）
      enabled: true
      compact: true             # 命中后先压缩上下文腾地方、再提醒它继续
      silent: true              # 管「光想不说」
      truncated: true           # 管「说了一半」（截断 / 代码块没闭合 / 悬空标点）
      promises: true            # 「我先去确认一下 X」这类句式（最软的一条，可关）
      maxAttempts: 2            # 同一轮最多提醒几次（两种情况共享）
      maxAgeMs: 300000          # 记录的有效期（毫秒）
      tailChars: 4096           # 判定用的正文尾部窗口（字符）
      message: '……'             # 提醒正文，会在会话里以一条 user 消息出现
    repeat:                     # 字符级复读检测
      enabled: true
      minChars: 4000
      checkEveryChars: 2000
      windowChars: 16384
      minPeriod: 8
      maxPeriod: 256
      minRepeats: 12
      minPatternDistinct: 4
      maxOffsetChars: 64
    lines:                      # 行级复读检测
      enabled: true
      windowLines: 240
      maxPeriodLines: 24
      minRepeats: 5
      minLineChars: 4
      maxOffsetLines: 24
    loop:                       # 短句打转检测（默认值极度保守，一般不用动）
      enabled: true
      minChars: 1500            # 累计输出这么多字符后才开判
      checkEveryChars: 1000     # 每新增这么多字符判一次
      windowChars: 8192
      maxAverageLineChars: 16   # 平均行长超过它就出局（正常长文是 20~60）
      maxSentenceChars: 24      # 多长的句子还算「短句」
      minRepeat: 4              # 同一句至少出现几次才算重复句
      minSentences: 50          # 至少要这么多短句才判
      minShortRatio: 0.85       # 短句要占「全部句子」的比例
      minRepeatRatio: 0.6       # 短句里重复句要占的比例
      confirmRounds: 2          # 连续命中几次才真的熔断
    tools:                      # 工具调用打转（动作层，只提醒不熔断）
      enabled: true
      windowSize: 12            # 记住最近多少次工具调用
      minCycle: 2               # 环的最短长度（2 = A→B→A→B）
      maxCycle: 3               # 环的最长长度
      minCycles: 3              # 同一个环至少重复几遍才算卡住
      canonicalize: true        # 参数比对前先合并多余空白与连续斜杠
      maxReminders: 2           # 同一个 agent 最多提醒几次
      message: '……'             # 提醒正文，会作为附加上下文跟着工具结果交回给模型
```

注意 patch 的语义是**整体替换 config**（不是深合并），所以要重述每一项想保留
的字段。只接受已知的键且类型正确，写错的项会被静默忽略并保留默认值 —— 这是
有意的，免得一条坏 YAML 让插件带着 `NaN` 静默失效。

设 `enabled: false` 可以整体关掉。

> **旧配置名仍然兼容**：早期版本这一组叫 `silentThought`（只管「光想不说」）。
> 老 profile 里如果还写着这个名字，插件照旧读得懂（`enabled` / `maxAttempts` /
> `maxAgeMs` / `message` 四个字段会搬到 `unfinished` 上），**不会因为改名而
> 静默失效**。新旧名字同时出现时以新名 `unfinished` 为准。

## 五、日志怎么看

启动时会有一行：

```
self-heal: 自愈已就位（墙钟上限 1800s，复读检测 开，短句打转检测 开，工具调用打转提醒 开，熔断后压缩并重试 开，没说完就继续的补救 开（命中后先压缩、再继续））。
```

每次介入也会留痕（`logTrips: true` 时）：

```
self-heal: 已熔断一次失控调用 [SELF_HEAL_REPEAT] | 路由 ... | 原因 检测到持续性复读（正文流）... | 已输出 612340 字符 | 耗时 41s
self-heal: 已熔断一次失控调用 [SELF_HEAL_LOOP] | 路由 ... | 原因 检测到短句打转（思考流）：同一批超短句反复出现，判定为卡住。 (426 个短句里有 426 个是重复句，最高频「好」×185) | 已输出 2574 字符 | 耗时 12s
self-heal: 已从熔断中恢复：历史已压缩，已把失败原因告诉模型，重新发送请求（本轮第 1 次）。
self-heal: 本轮输出未完成（正文停在「，」上，句子没有写完）：已压缩上下文（历史已变短），已注入提醒要求接着写完（本轮第 1 次）。
self-heal: 本轮输出未完成（只产生了思考内容，没有输出任何给用户看的正文）：找不到压缩服务，直接继续，已注入提醒要求接着写完（本轮第 1 次）。
self-heal: 工具调用打转：read_file → edit_file 已重复 3 遍，已注入提醒。
```

第二行那条「未完成」日志里，**冒号后面那句就是压缩的结果**，共四种：
`已压缩上下文（历史已变短）` / `压缩过，但这次没有可压缩的区间` /
`找不到压缩服务，直接继续` / `压缩失败（…），直接继续`。
括号里那句则是判定依据：`max-tokens` / `open-code-fence` / `dangling-punctuation` /
`pending-promise` / `no-content`。出问题时看这两处就够了。

搜 `self-heal:` 就能看到全部痕迹。一行都看不到，说明插件没加载（新插件通常
需要重启 DSH）。

## 六、自测与自检

```powershell
cd %USERPROFILE%\.dsh\external\dsh-self-heal

# 1. 单元 + 集成测试（161 个用例）
npm test

# 2. 契约自检：用真实的 DSH 包验证「接口没变、数据合法」（需要本机装有 DSH）
npm run contract

# 3. 诊断：看检测在真实事故文本上什么时候动手，以及性能
npm run diagnose

# 4. 校准：误报率 / 漏报率 / 检测延迟三张表（回答「会不会误伤正常输出」）
npm run calibrate
```

四者的分工：

- `npm test` —— 行为对不对（不依赖 DSH，任何机器都能跑）；
- `npm run contract` —— 依赖的接口还在不在。它会**用官方组装器解析我们伪造的
  熔断分片**、**用官方 Session 写入我们构造的提醒消息**、**在真实 Cordis 上下文里
  把三条链路跑一遍**，再检查官方默认重试白名单里确实没有我们的 code。DSH 升级
  后先跑它。
- `npm run diagnose` —— 触发点与吞吐（真实事故文本第几个字符被抓、每秒能处理多少）；
- `npm run calibrate` —— **判定质量**：拿 15 类正常输出（长文 / 代码 / 表格 / 清单 /
  对话 / JSON / 日志 / 中英混排 / 口头禅 …）与 6 类异常输出逐条过一遍，报出
  误报数、漏报数与检测延迟；再扫一遍阈值网格，给出「误报 ↔ 漏报 ↔ 延迟」的取舍。
  它还会跑一组**故意放宽**的对照档位，让你看到每道闸门到底在挡什么。
  改阈值之前先跑它。

> 如果 PowerShell 报「`npm.ps1` cannot be loaded because running scripts is
> disabled on this system」，那是执行策略挡住了解释器包装脚本，改用 `npm.cmd test`
> 或直接用 node：`node --test test/detect.test.mjs test/integration.test.mjs test/recovery.test.mjs`。

测试覆盖的极端场景（节选）：40 万字符的正常长输出必须完整放行、单个 100 万
字符的分片、10 万字符的超长单行、空输入与类型不对的分片、上游抛错必须原样
上传、熔断到次数上限后必须停手、压缩服务缺失/抛错/取消、载荷残缺、多会话
互相隔离、辅助调用不参与记账。

「没说完就停」这一组里，**「绝不能误报」的用例比「必须命中」的还多** ——
正常句号收尾、完整代码块收尾、表格收尾、列表收尾、省略号收尾、对用户交代
下一步、以问句收尾，全部必须放过；另有专门用例钉住「先压缩、再提醒」的顺序
（含压缩服务缺失 / 抛错 / 压不动三条降级路径，以及被用户中断后不许再打扰）。

## 七、性能

检测在每个 token 级分片上都会被调用一次，所以这块必须便宜：

| 场景 | 实测 |
|---|---|
| 正常中文输出 21.7 万字符（每片 8 字符，2.7 万次） | 约 17 ms |
| 同一样本（每片 64 字符） | 约 15 ms |
| 「没说完」判定用的尾部缓冲（同样本，2.7 万次） | 约 2 ms |
| 对照：尾部缓冲的最直观写法 `(tail + text).slice(-N)` | 约 33 ms |
| 整条插件链路（复读检测 + 尾部缓冲 + 记账）的净开销 | 约 6 ms |
| 短句打转判定：正常文本（走平均行长预检直接出局） | 约 3.5 微秒/次 |
| 短句打转判定：真在打转的文本（走完整统计） | 约 79 微秒/次 |
| 对照：优化前的旧检测实现 | 约 360 ms |

也就是说检测器能吃下 **1200 万字符/秒** 以上。真实模型输出通常在每秒几十到
几千字符，摊下来的 CPU 占用不到万分之一 —— 整条链路摊到每个分片约 0.2 微秒，
一次几秒钟的模型调用里完全感觉不到。短句打转那条线更便宜：正常文本连切句都
不做（平均行长预检直接排除），每 10 万字符输出只花约 0.35 ms。

实现上有五个关键点（都在源码注释里写明了原因）：

1. **节流**：输出累计超过 `minChars`（默认 4000）才开始判定，之后每新增
   `checkEveryChars`（默认 2000）才判一次 —— 不做逐字判定。
2. **廉价预检**：判定前先用几次 O(1) 的字符比较把绝大多数候选周期排除掉。
   这是「完全重复的必要条件」，所以不会漏判任何真实复读。
3. **惰性搬运**：不在每个分片上拼接 16KB 的判定窗口，而是攒到该判定的那一刻
   再合并；不同字符数的检查也改成「够数就收工」，不建集合。
4. **尾部缓冲同理**：判断「说没说完」只需要正文最后几千字，所以也是「先攒、
   后并」—— 攒够一个窗口才合并一次，内存固定在约两个窗口。最直观的
   `(tail + text).slice(-N)` 每次都要重拼整个窗口，实测慢 20 倍。
5. **短句打转先数换行**：判定前先算一次平均行长（只数换行符、零分配），
   正常长文（20~60 字符/行）当场出局，根本不会进入切句统计。

内存方面：每条流只保留尾部 `windowChars`（16KB）的复读窗口 + 同尺寸的短句
窗口 + `tailChars`（4KB × 2）的正文尾巴，**都不随输出总长度增长**。记账表按
会话存，并有 512 条上限。

## 八、已知边界（诚实清单）

1. **复读检测只做精确重复匹配。** 措辞略变的循环会绕过它 —— 这类现在由「短句
   打转」那条线兜住（只要它确实是一堆短句在打转）；若循环体是**长句**且在变
   换措辞，仍然只能靠墙钟超时兜底。
2. **低信息量周期被刻意放过。** 循环体内不同字符少于 `minPatternDistinct`
   （默认 4）时跳过，例如连续几百个 `=` 或 `-`。这是为了不误伤 Markdown 分隔
   线和代码缩进。
3. **输出短于 `minChars`（默认 4000 字符）完全不检测。** 短回答即使重复也不
   值得打断。
4. **工具参数不参与复读判定。** 批量生成同构记录是合法用法。
5. **没有跨轮会话预算。** 每次模型请求独立计数；多轮慢慢烧不在覆盖范围内。
6. **上游完全不返回数据时（连接卡死），墙钟检测也动不了手** —— 它只能在「拿到
   下一块数据」的时刻比较时间。这种卡死由官方的 `streamIdleTimeoutMs`（默认 5
   分钟无数据即中断）负责，两者是互补关系：官方管「不吐字」，本插件管「一直吐
   字但没完没了」。
7. **补救会在会话里留下一条 user 消息。** 这是必要的代价 —— 要让模型接着往下
   写，就得有东西告诉它。`source.kind` 是 `self-heal`，界面上能看出它不是真人
   打的。
8. **「最后一句像是在自我承诺」是一条启发式判据，可能误报。** 它只看最后一句
   （200 字符以内、不含「你 / 您」）是否匹配「让我…」「我先…」「接下来我…」
   「Let me…」这类句式。要是被它吵到，把 `unfinished.promises` 设成 `false`
   就行 —— 其余三条判据（截断 / 未闭合代码块 / 悬空标点）不受影响。
9. **压缩会让「本轮结束」晚几秒。** 命中补救时插件会等压缩跑完再提醒，而压缩
   本身要调一次模型出摘要。这是「先腾地方、再继续」的代价，且只在同一轮的
   第一次命中时发生。不想等就设 `unfinished.compact: false`（退化成直接催它
   继续）。
10. **如果某个 provider 配的是 `mode: 'always'` 的重试策略**，那它对任何失败都
    会重试（包括本插件的熔断）。此时请改用 normal 模式，或把本插件的
    `recover.enabled` 关掉，避免两套重试叠加。
11. **「短句打转」是统计判据，取向是「宁可漏判，绝不误报」。** 要动手必须**同时**
    满足五个条件：累计输出 ≥ 1500 字符、平均行长 ≤ 16 字符、≥ 50 个短句且短句
    占全部句子的 ≥ 85%、短句里 ≥ 60% 是重复句（同一句出现 ≥ 4 次）、**连续两次
    判定都命中**。因此它抓不到这两种：① 只持续一两百个字符的短暂打转；
    ② 长句为主、只是个别词重复的形态 —— 这两种留给墙钟超时兜底。
    这么保守的理由：**打断一次正常输出是不可逆的**（用户正看着回答就被掐断
    重来），而漏判只是多烧一点 token。你觉得它太吵可以直接 `loop.enabled: false`。
12. **正常输出绝不会因为「句子短」或「有口头禅」而被判为打转。** 这两点各有
    专门的反例用例钉住（「短句多但各不重复」「好的。重复 60 次 + 一堆长句」），
    它们在集成测试里必须被完整放行到最后一个分片。
13. **工具调用打转只看「参数也几乎一样」的重复。** 判据是「工具序列成环 ≥ 3 遍
    **且** 环内对应位置的参数归一化后完全一致」。所以：正常的「读 A → 改 B → 测 C」
    （每次参数不同）**不会**被提醒；参数变化更大的循环也抓不到。另外它与 DSH
    自带的 `dsh-repeat-tool-reminder`（同一个工具、相同参数连续 N 次）是**互补**
    关系，两者可能在不同时机各提醒一次。
14. **熔断诊断会往会话里多写一条 user 消息。** 百来字，换来的是「重发不再是盲目
    的」—— 重复坍缩是近乎确定性的吸引子，不说清病类，重发大概率原样再犯。
    嫌它多可以设 `recover.explainFailure: false`；它会出现在会话历史里，重启后
    读档不受影响（已有契约自检覆盖）。

## 十一、和外面那些方案比，我们在哪一层

做过一次同类方案调研（报告：[docs/DSH插件-失控自愈-同类方案对比调研-20261009.md](../../docs/DSH插件-失控自愈-同类方案对比调研-20261009.md)），
结论摆在这儿，免得高估自己：

| 层 | 别人 | 我们 |
|---|---|---|
| 解码 / 采样（改 logits，最根本） | HuggingFace `repetition_penalty`、OpenAI `frequency_penalty`、**DRY**（llama.cpp 等已采用）、vLLM 引擎内 `RepetitionDetectionParams` | **完全没有**（DSH 的 `GenerateOptions` 不暴露这些字段，够不着） |
| 推理引擎 | vLLM 检测到重复就提前结束生成 | 无（走远程 API，没有本地引擎） |
| Agent 框架 | LangGraph `recursion_limit`、OpenAI Agents SDK `max_turns`、Claude Agent SDK `max_budget_usd` | 部分等价，但那些是「停」，我们是「救」 |
| 工具调用行为 | `agent-loop-guard`（四策略 + WARN/STOP/ESCALATE）、AutoGPT circuit breaker | 本轮补上（只提醒） |
| **输出文本流** | **`simurg`**（conformal 误报预算、零泄漏缓冲、Self-Heal 带诊断与裁边界、有论文与 TPR/延迟指标） | **我们在这层**：多一条「行块周期 + 末尾相位偏移」检测与「没说完就停」补救；但**没有统计学校准，也没有带标签语料的评测**（只有 `npm run calibrate` 的合成语料） |

一句话：**在最根本的那一层我们够不着，在公开方案最成熟的那一层（流式检测）我们不是最先进的，
但我们守的位置别人没占** —— 宿主层拦截、不挑协议、自愈而不只是掐断。

## 九、从旧版迁移（`dsh-loop-guard` → `dsh-self-heal`）

1. 源码目录改名（仓库里已用 `git mv` 完成）；
2. 部署目录：`external\dsh-loop-guard` → `external\dsh-self-heal`；
3. junction：`profiles\<名字>\node_modules\dsh-loop-guard` 改成 `dsh-self-heal`；
4. `profiles\<名字>\package.json`：`dependencies` 与 `dsh.profile.bundles` 里的
   名字一并改掉；
5. 如果 profile / home 的 `cordis.patch.yml` 里有按 id 写的覆盖，把
   `id: loop-guard` 改成 `id: self-heal`，并删掉已经废除的 `maxOutputTokens` 字段；
6. 重启 DSH（新包通常不在热重载范围内），确认日志里出现 `self-heal: 自愈已就位`。

更名只影响「怎么被加载」，不影响能力本身：新代码是旧代码的超集（多了压缩重试
与「光想不说」的补救），唯一的删减就是去掉了单次输出上限。
